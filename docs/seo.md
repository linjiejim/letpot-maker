# Search visibility

LetPot Maker renders indexable HTML for the landing page and both browser tools. SEO-critical output is generated by the application rather than injected by a client-only script.

## Implemented foundation

- Every public page has a unique title, description, canonical URL, Open Graph URL, share image, and Twitter card.
- `/robots.txt` allows public pages, blocks API routes, and advertises `/sitemap.xml`.
- `/sitemap.xml` contains the three canonical public routes and excludes query-string Studio variants.
- `/manifest.webmanifest`, the SVG favicon, the `WebSite` site name, and consistent social metadata establish a single site identity.
- The landing page exposes `WebSite` and `SoftwareApplication` JSON-LD. Each browser tool exposes truthful `SoftwareApplication` data, including its zero-price offer.
- Tool pages have one descriptive page-level `h1`, and all public pages are connected by crawlable HTML links.
- Production route tests assert the rendered metadata and crawler endpoints.

Google ignores the `keywords` meta tag, so the project deliberately does not generate one. Search terms should appear naturally in accurate titles, descriptions, headings, links, and useful visible content.

## Production configuration

Set the public origin without a path or trailing slash:

```dotenv
LETPOT_SITE_URL=https://maker.example.com
```

This value takes precedence over request headers and deployment-provider URLs. It should be the only HTTPS origin that serves the site; redirect alternate hosts and HTTP traffic at the reverse proxy.

Optional ownership tokens can be added without code changes:

```dotenv
GOOGLE_SITE_VERIFICATION=token-from-search-console
BING_SITE_VERIFICATION=token-from-bing-webmaster-tools
```

Do not copy the full verification `<meta>` element into these variables—use only its token value.

## Post-deployment checklist

1. Confirm `/`, `/studio`, and `/pod-styler` return `200` without authentication or a crawler challenge.
2. Inspect the page source and confirm each canonical, `og:url`, JSON-LD URL, and sitemap entry uses the final HTTPS origin.
3. Open `/robots.txt`, `/sitemap.xml`, and `/manifest.webmanifest` directly and verify their content types and URLs.
4. Add the exact origin property in [Google Search Console](https://search.google.com/search-console/about), verify ownership, and submit `/sitemap.xml`.
5. Run the landing page and tool pages through Google’s [Rich Results Test](https://search.google.com/test/rich-results) and URL Inspection. Structured data makes a result eligible; it does not guarantee a rich result.
6. Add the site to [Bing Webmaster Tools](https://www.bing.com/webmasters/about), then submit the same sitemap.
7. Run Lighthouse against the production origin on mobile and desktop. Track field Core Web Vitals after enough real traffic exists; the WebGL tools are intentionally heavier than the landing content.

Search Console, Bing registration, DNS redirects, backlinks, and useful community content are external operational work and cannot be completed inside the repository.
